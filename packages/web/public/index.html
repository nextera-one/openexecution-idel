Protocol Zero

Not prettier Bash.

A policy-aware execution runtime that turns human or AI intent into safe, logged, cross-platform execution. IDEL is the intent language; the runtime parses it, classifies its risk, enforces policy, and records every decision to a signed, append-only audit log — before anything touches disk.

The killer demo

The same typo that nukes a laptop in a normal shell is refused here — and the refusal is itself an audited event. 

$ idel remove.folder name=/ recursive=true force=true

Command: remove.folder
Risk: CRITICAL
  - [CRITICAL] root-delete: Destructive target resolves to the filesystem root (/).
  - [HIGH] recursive-force: Destructive op uses recursive + force together on /.
Decision: BLOCK [rule #0]
Reason: Matched rule 0 (action: block).
BLOCKED. No files were changed.
Log: ~/.idel/logs/openlogs.jsonl

Exit code 4. No filesystem traversal happened — the runtime short-circuits a CRITICAL classification and refuses to even walk /. --yes does not clear it: the CRITICAL floor is enforced by the policy engine itself.

Why this exists

Traditional shells hide risk in flags and symbols. rm -rf /, chmod -R 777 /, and dd if=x of=/dev/sda are one typo from catastrophe, and nothing about them is reviewable, audited, or policy-gated. IDEL exposes risk at the call site and lets the runtime decide.

🛡️ Safety

Destructive intent must be explicit (recursive=true force=true). Catastrophic targets — root, home, drive roots, raw devices, recursive 777 on broad trees — are blocked by a non-overridable floor.

📜 Auditability

Every command, risk decision, adapter, exit code, and duration is appended to a signed, hash-chained JSONL trail — with secret redaction before signing.

⚖️ Policy

allow / warn / require-dry-run / require-approval / block, matched on risk, command, params, source, and environment. Built for CI and team enforcement, not just an interactive prompt.

🧭 Portability

Execution is adapter-based (POSIX, PowerShell, in-process Node) — not "compile to Bash." Where platforms genuinely diverge, the registry says so honestly.

One linear pipeline

Each command flows through the runtime exactly once. The runtime — not the model, not the shell — is the enforcement boundary.

  1. parse verb.scope param=value → typed AST
  2. resolve command in the registry (custom > official > core)
  3. coerce type-check params, fill defaults, reject unknowns
  4. safety two passes (AST + resolved real-path); effective risk = MAX
  5. policy map risk + match → allow / warn / dry-run / approval / block
  6. plan pick an adapter, build a real argv (no string templates)
  7. execute run the plan (or simulate for dry-run / block)
  8. openlogs append one signed, redacted audit record
Two precedence systems, pointing opposite ways. Registry content resolves custom > official > core (a team can shadow a definition). Core safety floors resolve core > everything (a CRITICAL classification can never be cleared — not by a custom registry, a lax policy, or --yes).

Teach IDEL any installed CLI

Install a tool, and IDEL can learn it. idel learn introspects a CLI's own --help, drafts conservative IDEL command definitions locally, and validates each against the registry schema — fail-closed. Accepted drafts land in the custom layer and are then governed by the same runtime: risk-classified, policy-gated, audited. 

$ idel learn gh --write

Introspecting "gh" and drafting IDEL commands…
Learned gh  (7 accepted, 2 rejected)

  ✓ clone.gh.repo    [MEDIUM]  Clone a repository into a new directory.
  ✓ create.gh.pr     [LOW]     Create a pull request.
  ✓ merge.gh.pr      [HIGH]    Merge a pull request into its base branch.
  ✓ delete.gh.repo   [CRITICAL] Permanently delete a repository.
  ✗ import.gh.alias  — adapters.posix: args[1] unknown arg kind

✓ wrote 7 learned command(s) to ~/.idel/registries/custom/learned-gh.json

A learned delete-shaped command is classified by the same two-phase safety engine as a hand-written one. Learning a destructive tool weakens no guarantee. Preview is the default; --write persists.

Ask AI, on the runtime's leash

The embedded AI console doesn't wrap a model around the runtime — it puts the runtime in front of AI. The model proposes an IDEL command; the runtime parses, classifies, applies policy, and executes (or refuses). A CRITICAL command the model hallucinates is blocked by the same floor that catches a human typo, and recorded as source: "agent".

Propose, then confirm

Every write/move/delete is dry-run first. Before any real run, the web console pauses and asks you to Approve or Decline — the agent never auto-approves, and a decline leaves the dry-run result standing.

Key stays server-side

The Anthropic call happens in the idel serve process, over a loopback-only bind. Your key never reaches the browser.

OpenLogs: tamper-evident by construction

Every command produces exactly one record. Each is TPS-stamped, SHA-256 hash-chained to its predecessor, and Ed25519-signed with a machine-local key. Break a link — edit, reorder, or delete a record — and verification flags the exact index.

  • Secret redaction runs before signing (by key name and by value shape: JWTs, sk-…, AWS keys, GitHub PATs).
  • A policy block is a normal signed audit event (result: blocked_before_execution), not an error.
  • The chain verifies programmatically; the log is append-only.
